# Acknowledgments: images and private communications

Use the existing portal delta release and rollback workflow. First reconcile the shared header and Acknowledgments files with production; this branch is based on the prior Acknowledgments release, not a production export. Back up affected files and the database. Apply `database/ack-communication.sql` before enabling new code. The migration creates three tables and does not rewrite signatures, audit events, schedules or employee records. Roll back files to disable the UI, but retain the new tables and events so no correspondence is lost. Image upload needs PHP GD, sufficient request/packet limits, and restricted backups.

**Named inbox:** configure `ACK_CONTACT_OWNER_ID` to the verified employee ID of the designated active Owner. A different admin is not the private inbox owner. Questions on an instruction are part of its existing recipient-specific acknowledgment history and can be reviewed under existing acknowledgment permissions. Private assistance is a separate inbox.

**Anonymous intake:** publish only `standalone/ack-anonymous/` at the root of a dedicated HTTPS origin outside the portal cookie domain. Do not put this on an authenticated portal route. Only the portal gets the named inbox API. On both services set the same designated Owner ID, `ACK_ANON_ORIGIN` and random high-entropy `ACK_ANON_GROUP_SECRET` (at least 32 bytes). On intake only set `ACK_ANON_DSN`, `ACK_ANON_DB_USER`, `ACK_ANON_DB_PASSWORD`; restrict its database grant to SELECT and INSERT on the anonymous table only. Use TLS to the database. Never place configuration or keys in public files. No portal session, uploads, notification, analytics, tracking scripts, integration or time field on anonymous reports. Access codes are bearer secrets: only a hash is stored; the Owner cannot recover them.

**Privacy gate:** before setting `ACK_ANON_PRIVACY_READY=1`, verify the entire hosting path (including CDN, WAF, proxy, PHP, host, database, backups and any analytics/possible portal outbound-click tracking) does not retain data allowing the Owner to correlate a submitter, IP, time or code with a report. Disable access/body/query/SQL tracing and session auto-start/cookies on intake. Serve all intake assets with no-store, no-referrer and no third-party scripts; set CSP frame-ancestors 'none' by HTTP header. Do not forward identifying headers to the intake application. Only enable if these controls can be verified. Shared group tickets rotate daily and are identical for all staff; they are not employee credentials. Use infrastructure-wide abuse controls that do not keep per-sender logs. Test with two employees and the Owner, including a second administrator denied access, before rollout. No software can prevent a reporter from identifying themselves in the text.

**Release smoke test:** send a test acknowledgment to controlled test users, check View image and X (including mobile), separate understanding, question/answer/Owner reply and schedules. Confirm the assigned employee alone can record their view. Open both chat routes from above Online. Check no dashboard transcript; collect the anonymous code, close the browser, retrieve the Owner reply by code alone; verify no code or identity appears in the Owner response or logs. Do not use real employee reports for tests.
