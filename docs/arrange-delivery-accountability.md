# Arrange Delivery: compact accountability release

## Scope

The existing Order Details delivery tab is retained. No Order Board redesign, payment migration, historical backfill or driver SLA is introduced. Jost is inherited from the portal, with 10.5px/500 section titles, 9.5px labels and regular-weight inputs. Packed By and Arranged By sit immediately beneath the payment summary.

## Evidence and state rules

- Payment uses the existing order allocation/balance reader and paid-confirmation flag. Checking Paid opens the existing payment editor; it never posts a payment. A financial/board disagreement needs verification. Unpaid and partial orders require explicit COD confirmation. Delivery and cash receipt do not themselves mark an order paid.
- Arranger and handover identities come from the authenticated employee. A current assignment alone is not proof of packing; the read model uses recorded packing-stage evidence and explicit reviewed packer corrections. Missing attribution remains labelled for review.
- Queue, sent, seen and accepted are distinct. Acceptance is an explicit assigned-driver command, not notification acknowledgement. Reassignment invalidates old acceptance/custody while preserving those events in history.
- New tracked arrangements require acceptance plus Front handover (actual parcel count) and driver pickup confirmation before start. An authorised Front exception requires a recorded reason. Legacy arrangements remain operable without fabricated evidence or retroactive prerequisites.
- Completion records recipient, method, optional proof reference (mandatory for photograph/signed receipt methods), confirmer and note. Manual confirmation additionally requires an authorised employee and reason. Existing cash reconciliation gates remain unchanged.
- Customer-requested time is not a guaranteed driver SLA. The new request does not generate driver lateness notifications.
- COD coordination retains the existing eight-business-hour deadline from dispatch. Exception-based dispatch also records its clock. The scanner emits one overdue event per dispatch and retains it after resolution. It notifies Front; it does not automatically deduct employee performance. Scheduler events explicitly identify themselves as generated by the scheduler, not an employee click.
- All attempts, including cancelled attempts, stay visible. Historical facts are never rewritten by these read models.
- The tab polls every ten seconds while visible. Status updates preserve unsent parcel/confirmation input. Money verification is re-read after returning from the payment editor. Mutation requests use the existing authenticated/CSRF-protected API and UUID transaction guard.

## Verification performed locally

`tests/run-delivery-accountability.ps1` launches a random-password, loopback-only synthetic MariaDB and runs the existing arrangement regression suite plus `tests/delivery-accountability.php`. Synthetic databases are dropped by the fixture. Production records are never used for test writes.

`node tests/order-delivery-panel.cjs` checks desktop 1100px, mobile 390px and 320px: no hard-coded driver, payment editor without silent writes, COD confirmation/cancel, prepaid dispatch, saved-order reopening, accountability time display, cancelled history, safe message rendering, and refresh preserving the parcel-count draft. It uses only a local mock server and headless Chrome.

PHP syntax and JS syntax checks must pass for changed files. Use PHP 7.4+ (the code uses the repository's existing language level).
