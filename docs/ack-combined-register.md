# Combined Acknowledgements register

The existing Admin Acknowledgements register lists one row per recipient/instruction version, private assistance topic, or anonymous report. Clarification changes the type of the instruction thread, not its identity. The Type filter covers all four kinds. The previous Admin Messages & Assistance link opens this register. Employees keep their existing entry points. Only the designated inbox owner can see private assistance and anonymous reports; another administrator's access to acknowledgements does not grant this access.

New anonymous messages store only a Namibia calendar **date**, role (“reporter” or “owner”), text, a random report reference and delivery bookkeeping. The public reference is not the reporter's private reply code. Never put the private code in an alert, URL, analytics, register row or error log. The owner-only alert shows the public reference and a short message preview, not account metadata. An immediate alert can reveal the approximate arrival time, and message text can identify its author. The employee sees this warning before sending.

Opening a thread reads it. Deferring an alert leaves it unread. Neither signs an instruction. Only explicit employee confirmation acknowledges understanding. An assistance conversation shows **Awaiting reply**, **Replied**, or **Reply received**; these are not instruction completion states. Named messages have timestamps. Anonymous messages have dates only; unknown historical dates stay unknown.

Acceptance: Start two assistance topics as one employee, defer the first alert, and reply to the older topic from the Admin table. The reply must arrive in the existing employee conversation; a follow-up must make only that topic unread. Reload and repeat delivery: no duplicate thread or reply. A second administrator and a different employee must be unable to open it. For anonymous reports, verify a public reference cannot retrieve a private reply, the owner can respond without leaving the register, and no name or exact time is displayed. Test all four type filters on desktop and mobile.

## Migration and release

1. Check the schema and live versions of both intake paths. Back up the anonymous tables and related portal files privately. Do not export report bodies, codes or hashes into CI artifacts.
2. Pause assistance and report writes on both intake and management paths. Before switching readers, apply `database/ack-combined-register.sql` and check message counts, assistance topic links, and retained anonymous replies. Assistance links use existing explicit topic boundaries (earlier unmarked messages belong to the first thread); message bodies are not rewritten. Existing assistance notifications already read or deferred must not be replayed. Legacy anonymous dates remain null; the UI shows **Date not recorded**. The migration cannot reconstruct overwritten replies.
3. Deploy the matching portal code and any enabled standalone intake together. The portal imports `standalone/ack-anonymous/Store.php` as a library. For a separately hosted intake, also update its own copy, client and notice; retain the existing isolated-origin and log/privacy controls. Grant intake only the reads/inserts needed for its append-only thread, never owner-action access. Do not use old reply writers after migration.
4. Test using controlled fixtures: designated owner vs second admin; fresh code vs public reference; duplicate send vs genuine follow-up; date-only history vs unknown legacy dates; open vs dismiss; mobile and desktop opening without navigation. Keep intake writes paused if rollback would leave a reader unable to see new messages.

The earlier release note's “no time field / notification” approach is superseded **only** by this date-only, owner-only requirement. Do not add employee-linked telemetry, notification actors, an exact timestamp or a connection between staff logins and reports.
